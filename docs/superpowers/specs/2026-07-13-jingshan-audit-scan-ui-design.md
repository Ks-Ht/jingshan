# 净山 M28 全面审计、扫描增强与 UI 交互重构设计

**日期：** 2026-07-13  
**状态：** 已确认设计，待实施  
**视觉方向：** A「克制现代水墨」  
**适用版本：** 本地 v0.9.0 / M27 后续迭代

## 1. 背景与结论

净山已经具备可信的核心安全骨架：扫描与删除分离、普通文件默认进入废纸篓、关键路径拒绝列表、永久删除显式确认、运行中应用保护、清理历史与恢复能力。本轮不重写这套骨架，而是在其上解决四类真实问题：扫描结果无法表达“不完整”、已知安全缓存覆盖不足、部分跨模块流程存在竞态或重复、界面虽有鲜明水墨特色但信息层级和操作闭环仍不够成熟。

本设计的核心判断是：**增强发现能力，但不扩大默认删除权；提升信息密度，但不牺牲净山的留白和水墨辨识度。**

## 2. 目标

1. 让用户明确知道扫描是否完整，以及哪些目录因权限、读取错误或取消而未覆盖。
2. 扩充浏览器、开发工具、AI 工具和卸载残留的已知安全覆盖，同时保持保守默认选择。
3. 修复 Apple 缓存过度保护、跨模块重复计数、扫描回调竞态、外置卷恢复等可靠性问题。
4. 收敛重复的清理执行流程，使成功、跳过、失败和历史记录在各模块保持一致。
5. 将现有“墨韵 Studio”升级为更克制、更专业的 macOS 原生体验，形成完整的扫描—检查—确认—结果—恢复闭环。
6. 补齐键盘、VoiceOver、Reduce Motion、深浅色和大字号支持。

## 3. 非目标与安全边界

- 不引入 `sudo`、提权 helper、后台常驻清理或静默自动删除。
- 不默认勾选来源不明、归属不确定、可能包含用户内容的项目。
- 不扫描并自动删除系统级 LaunchDaemon、收据数据库、共享 Group Containers 等高风险位置。
- 不改变 Docker daemon 资源必须经 Docker CLI 清理的边界；宿主文件仍经 `DeletionEngine`。
- 不将永久删除变成主路径；废纸篓仍是默认且推荐方式。
- 不用动画、玻璃拟态或大面积装饰性水墨压过内容。
- 不在本轮加入重复文件、定时清理、命令面板、国际化或需要私有 API 的硬件监控。

## 4. 审计发现与优先级

### P0：结果可信度与数据安全

1. 多个扫描器通过 `try?` 把读取失败折叠为空数组，界面无法区分“没有内容”和“没有扫到”。
2. `com.apple.*` 通配保护范围过粗，Safari 等已知安全缓存可能被标记为受保护且无法清理。
3. 外置卷文件进入该卷的 `.Trashes/<uid>` 后，恢复逻辑若只信任 `~/.Trash` 会拒绝合法恢复。
4. Docker 宿主缓存可能同时出现在通用用户缓存结果中，造成跨模块重复展示和容量重复计算。

### P1：流程可靠性与可维护性

1. Purge、Large Files 等扫描的迟到进度回调可能污染下一代扫描结果，需要统一代次令牌。
2. 多个 ViewModel 重复实现删除循环、结果汇总、历史记录和重扫逻辑，容易产生行为分叉。
3. 完成提示以聚合数字为主，用户无法定位具体失败、跳过或需要重试的项目。
4. 主窗口与菜单栏可能重复采样同一系统指标，存在不必要的后台工作。

### P2：覆盖率与体验

1. 浏览器显式规则主要覆盖顶层 Cache，未覆盖 Chromium 多 Profile 的 Code Cache、GPU/Shader Cache、Crashpad 等可再生成内容。
2. 开发工具覆盖已较广，但 Xcode 文档/设备日志、模拟器临时数据、Playwright、Corepack、Deno 和更多 AI 工具缓存仍可补齐。
3. 卸载残留缺少 ByHost Preferences、Cookies、DiagnosticReports、Application Scripts，以及引用应用路径的 LaunchAgent 提示。
4. 页面结构、筛选、底部操作条和结果明细不统一，清理页的整组交互存在重复点击语义风险。

## 5. 扫描架构

### 5.1 数据驱动规则

将零散路径规则收敛为可测试的规则描述。规则至少包含：

```swift
public struct ScanRule: Sendable, Hashable {
    public let id: String
    public let module: ScanModule
    public let source: ScanSource
    public let path: ScanPath
    public let purpose: String
    public let risk: ScanRisk
    public let defaultSelection: DefaultSelection
    public let runningAppPolicy: RunningAppPolicy
    public let ownership: RuleOwnership
}
```

- `ScanModule`：Clean、Docker Host、Purge、Uninstaller 等唯一归属。
- `ScanSource`：应用、浏览器、开发工具、AI 工具、系统辅助位置等展示来源。
- `ScanPath`：固定路径、bundle id 路径、受约束 glob、多 Profile 路径或经过验证的解析器。
- `ScanRisk`：`safeRegenerable`、`reviewRecommended`、`protected`。
- `DefaultSelection`：仅 `safeRegenerable` 可根据普通模式规则默认选择；强力模式和建议检查项一律不预选。
- `RunningAppPolicy`：允许扫描但禁止选中、直接跳过、或不受影响。
- `RuleOwnership`：用于跨模块去重，任何实际路径只能有一个主模块所有者。

规则系统只描述发现与归属，不直接执行删除。所有普通文件的实际删除继续进入现有 `DeletionEngine`。

### 5.2 显式扫描状态

每个扫描区域返回项目与状态，而不是只返回项目数组：

```swift
public struct ScanAreaResult<Item: Sendable>: Sendable {
    public let area: ScanArea
    public let items: [Item]
    public let status: ScanAreaStatus
    public let issues: [ScanIssue]
}

public enum ScanAreaStatus: Sendable {
    case completed
    case partial
    case permissionLimited
    case failed
    case cancelled
}
```

`ScanIssue` 保存区域、用户可读说明、底层错误分类和建议动作，不把敏感完整路径写入遥测；净山当前仍保持纯本地处理。

聚合扫描状态规则：

- 所有区域完成：显示“扫描完成”。
- 有项目但存在失败或权限缺口：显示“扫描完成，但结果不完整”。
- 全部区域因权限失败：显示权限受限空态，不显示“未发现可清理内容”。
- 用户取消：保留已发现项目并明确标注“已取消”，迟到回调不得再修改状态。

### 5.3 结果分类

清理结果固定分为四类：

1. **安全可清理**：已知可再生成、归属明确、通过所有路径与运行状态检查。
2. **建议检查**：可能可清理，但存在时间、来源、共享范围或用户内容不确定性；默认关闭，不支持整组全选。
3. **已保护**：命中运行中应用、关键路径、系统保护或规则明确禁止；不可勾选并展示原因。
4. **扫描问题**：权限不足、读取失败、取消或目录结构异常；提供重试、打开设置或查看说明动作。

容量总计必须区分“安全可清理容量”和“建议检查容量”，首页不把后者计入可安全释放总量。

### 5.4 路径归一化与去重

- 所有候选项在进入展示前执行标准化 URL、符号链接策略、大小写敏感卷适配和所有权判定。
- 同一文件系统对象若被多个规则命中，只保留优先级最高的主规则，并记录命中来源用于诊断。
- Docker daemon 资源不参与文件路径去重；Docker Host 路径必须显式声明所有权，通用 Clean 规则排除这些路径。
- 不通过解析符号链接扩大扫描或删除边界。

## 6. 覆盖能力增强

### 6.1 浏览器与 Electron

新增受约束的多 Profile 规则，只匹配已知缓存子目录：

- Chromium 家族：各 Profile 的 `Cache`、`Code Cache`、`GPUCache`、`ShaderCache`、`GrShaderCache`、`DawnCache`。
- 浏览器级可再生成内容：Crashpad 完成报告、component/update 下载缓存；不触碰书签、Cookies、History、Login Data、Extensions 和用户配置。
- Safari：继续只覆盖明确的 Cache 路径；修复其因 `com.apple.*` 被过度保护的问题，但不放宽到其他 Apple 容器数据。
- Electron 应用：仅对已识别 bundle/app 的 `Cache`、`Code Cache`、`GPUCache` 等固定子目录建立规则，不遍历并猜测整个 Application Support。

运行中的浏览器或 Electron 应用可以展示缓存，但默认禁止选中，并提示退出应用后重试，避免清理正在使用的数据库或缓存索引。

### 6.2 开发与 AI 工具

在现有 Xcode、SwiftPM、Homebrew、npm、pip、Cargo、Gradle、Yarn、pnpm、Bun、Go 和 CocoaPods 基础上补充：

- Xcode：文档缓存、设备日志和模拟器中明确的临时/日志目录；DerivedData、Archives 和 DeviceSupport 继续保持不同风险说明。
- JavaScript 工具：Corepack、Playwright 浏览器下载缓存、Yarn 经典缓存；不触碰项目锁文件或全局安装清单。
- Deno 与常见编译器下载缓存：仅覆盖官方明确可再生成区域。
- AI 开发工具：对已识别工具的模型下载缓存、扩展缓存或日志建立独立规则；大型模型文件归入“建议检查”，展示来源、最近使用时间和大小，永不默认选择。
- `~/.cache` 不再以一个不可解释的大桶重复覆盖已有细分规则；能够识别的子项优先使用来源规则，未知子项保留为默认不选的建议项。

### 6.3 卸载残留

在现有 Caches、WebKit、HTTPStorages、Saved State、Logs、Preferences、Application Support、Containers 和 LaunchAgents 规则上增加：

- `~/Library/Preferences/ByHost` 中与 bundle id 精确匹配的 plist。
- `~/Library/Cookies` 中与 bundle id 精确匹配的数据。
- `~/Library/DiagnosticReports` 中可由应用可执行文件名精确归属的崩溃/诊断报告。
- `~/Library/Application Scripts/<bundle-id>`。
- 用户 LaunchAgent：除文件名匹配外，可解析 plist 并在 `Program`/`ProgramArguments` 明确引用目标应用或其 helper 时列出。

以下内容只作为提示，不进入一键卸载选择：

- 共享 Group Containers。
- `/Library/LaunchAgents`、`/Library/LaunchDaemons`、系统级 Application Support 等需要管理员权限的位置。
- 归属仅靠相似名称推断的文件。

卸载确认页按“应用本体、明确残留、建议检查、系统级提示”分组，让用户知道哪些会移动到废纸篓、哪些需要手动处理。

## 7. 清理、恢复与并发流程

### 7.1 统一扫描代次

所有异步扫描使用递增 `generation` 或不可复用 token。进度、完成和错误回调在更新 UI 前必须验证 token。取消会使当前 token 失效；新扫描不继承旧扫描的迟到回调。Clean、Purge、Large Files、Uninstaller 和 Docker Host 文件扫描采用同一约定。

### 7.2 CleanupExecutor

新增 App 层统一执行器，负责：

- 按选择快照顺序执行；
- 将已扫描的 `precomputedSizeBytes` 传给删除引擎；
- 汇总成功移入废纸篓、永久删除、受保护跳过、运行中跳过和失败；
- 收集可恢复的 `TrashedItem` 并写入历史；
- 保留每项结果供 UI 展示；
- 支持取消后停止下一项，但不回滚已完成项目；
- 完成后由调用方决定重扫，避免执行器直接耦合某个 ViewModel。

Docker daemon 清理继续使用独立 CLI 执行器，但复用同一种结果展示模型；Docker Host 文件可以使用 `CleanupExecutor`。

### 7.3 外置卷废纸篓恢复

恢复信任根不能只写死 `~/.Trash`。删除时根据 `resultingURL` 与原始卷，保存经过标准化的可信 Trash 根及文件指纹；恢复时重新验证：

1. 结果路径仍位于同一卷合法的 `.Trashes/<uid>` 或用户主废纸篓内。
2. 当前文件指纹与记录一致。
3. 原始目标路径仍为空，且父目录创建不会越过安全边界。
4. 不覆盖已有文件，不跟随符号链接，不接受记录被篡改后的任意搬移路径。

失败项保留在可重试列表，只有全部可恢复项成功后才把记录标记为完全恢复。

### 7.4 指标采样

主窗口和菜单栏通过共享的只读指标采样服务订阅同一快照。无订阅者时停止高频采样；菜单栏关闭后不保留常驻采样。视图只格式化展示，不自行启动第二套系统探针。

## 8. 信息架构与页面设计

### 8.1 全局结构

- 保留顶部七模块胶囊导航和现有模块色，但降低轨道与阴影的存在感。
- 使用统一 `ModulePageScaffold`：页面标题/诗句、主指标、状态或动作、内容区、底部操作区。
- 首页负责回答四个问题：系统是否健康、可安全释放多少、是否有建议检查项、最近扫描是否完整。
- 首页模块入口不再全部同权堆叠：常用清理动作优先，状态、历史和其他工具作为次级信息。

### 8.2 首页

首页 Hero 保留山脊、水墨洗底和品牌诗句，但控制装饰面积。核心内容包括：

- “可安全释放”主数值和最近扫描时间。
- 一个明确主按钮“开始扫描”，一个次按钮“查看建议项/扫描结果”。
- 扫描完整度状态：完整、部分、权限受限或未扫描。
- 系统概览使用紧凑三列/四列指标，不重复绘制大型仪表盘。
- 模块入口采用低阴影卡片，显示模块状态和一条最重要数据，不用等权大色块。
- 清理历史保留累计释放、次数和恢复入口。

### 8.3 清理结果页

页面从上到下为：

1. 统一 Hero：总览、扫描状态、重新扫描/取消。
2. 搜索与筛选：全部、安全可清理、建议检查、已保护、扫描问题；支持按大小、来源、名称排序。
3. 结果分组：分组头本身是单个语义化 Button，展开和选择不叠加手势。
4. 项目行：原生 Toggle 或 Button 语义，完整键盘焦点、VoiceOver 标签、来源、路径摘要、大小、原因和状态。
5. 粘性底部操作条：已选数量与大小、默认“移到废纸篓”说明、主动作“检查并清理…”。

强力模式保留，但改为“扩展扫描范围”的明确说明。开启后所有项目都不预选，建议检查分组无整组全选。模式切换会开始新一代扫描并作废旧回调。

### 8.4 确认与结果闭环

确认 sheet 展示：

- 将处理的项目数、总大小和模块来源。
- 默认操作“移到废纸篓，可恢复”。
- 受保护与建议项的额外风险说明。
- 永久删除仅在设置允许且用户显式切换后出现二次确认。

结果不再只用聚合 Alert。统一结果 sheet 包含：

- 成功释放容量和项目数。
- 失败、跳过、受保护项目的可展开明细及原因。
- “重试失败项”“打开废纸篓”“查看清理历史/恢复”“完成”动作。
- dry-run 明确标记为预览，不写入清理历史。

### 8.5 其他模块一致性

- Docker：区分 daemon 资源与宿主文件，清理方式和可恢复性必须逐组标识。
- Purge：突出项目根目录、构建系统和“可重新生成”，建议项默认关闭。
- Large Files：强调这是用户文件，全部默认不选；提供目录、最近使用时间和打开 Finder 动作。
- Uninstaller：展示应用本体与残留层级，系统级提示不伪装为可自动处理。
- Status：保持 Bento 结构，但与清理页共享卡面、字阶和状态色，不增加装饰性动画。

## 9. 视觉系统

### 9.1 设计原则

- **克制现代水墨：** 水墨只承担品牌、Hero 和空态气氛；数据区以安静纸面和精确排版为主。
- **原生 macOS：** 尊重窗口缩放、键盘、焦点、菜单命令、系统设置和标准控件语义。
- **状态优先：** 颜色先表达模块和风险，再表达装饰；同一风险全 App 使用同一语义色。
- **少层级阴影：** 用 0.5pt 发丝线、微妙表面色和留白建立层级，不用连续嵌套卡片。

### 9.2 视觉令牌

- 浅色背景：暖纸白；卡面与背景仅保留轻微明度差。
- 深色背景：墨夜三层；卡面优先使用描边和微亮面，不使用发灰的大阴影。
- 品牌绿保留，模块色降低饱和度；风险色统一为墨绿、琥珀、墨红。
- 卡片圆角 14–16pt，紧凑控件 8–10pt，胶囊仅用于导航和短状态。
- 发丝线 0.5pt；默认卡片阴影轻且短，Hover 只上移 1–2pt。
- Hero 大数字使用圆角字形；正文、说明和路径保持系统易读字形与清晰层级。
- 动画以 150–240ms 淡入、数值过渡和短位移为主；Reduce Motion 下取消位移和弹簧。

## 10. 可访问性与交互标准

- 所有可点击区域至少满足舒适的 macOS 点击尺寸，不用仅靠颜色区分状态。
- Toggle、分组头、筛选器和底部主动作都能通过键盘访问，并有可见焦点环。
- VoiceOver 读出项目名称、选择状态、大小、风险、保护原因和可执行动作。
- 自定义复选框若无法完整继承 Toggle 语义，改为语义完整的 Button/Toggle 组合，不用裸 `onTapGesture`。
- 支持大字号后不截断核心操作；路径和次要说明可以折行或 tooltip。
- 浅色、深色和高对比模式分别验证文字、边界、禁用态和风险色。
- 权限失败提供打开系统设置动作；错误说明避免只显示技术错误码。

## 11. 状态与数据流

```text
用户开始扫描
  -> ViewModel 创建新 generation
  -> ScanCoordinator 执行模块规则
  -> 每个区域返回 items + status + issues
  -> 路径归一化、所有权去重、保护判定
  -> UI 分为安全/建议/保护/问题
  -> 用户筛选并选择
  -> 确认 sheet 生成不可变选择快照
  -> CleanupExecutor / Docker CLI 执行
  -> 逐项结果 + 可恢复记录
  -> 结果 sheet 展示成功/失败/跳过
  -> 用户重试、打开废纸篓或恢复
  -> 新 generation 重扫刷新真实状态
```

ViewModel 不直接拼装路径规则，也不自行实现删除循环；Scanner 只发现，Policy 只分类与保护，Executor 只执行，View 只呈现状态和触发意图。

- 离屏快照：首页、清理扫描中、完整结果、部分扫描、筛选、确认、部分失败结果、深色、大字号。
- 交互走查：键盘切换模块、展开分组、选择项目、取消扫描、确认清理、重试失败、打开废纸篓、恢复。
- VoiceOver 抽查：首页主动作、扫描状态、分组头、项目行、结果 sheet。

- 本地安装后进行启动、菜单栏、窗口缩放、权限受限和真实废纸篓冒烟测试。

### 12.3 完成标准

1. 用户能明确区分“没有垃圾”和“扫描不完整”。
2. 新增覆盖没有扩大默认高风险选择，强力模式仍全部手动选择。
3. 同一路径不会跨模块重复计数。
4. 所有异步扫描均不受旧代回调污染。
5. 内置盘与外置卷的合法废纸篓项目均能安全恢复。
6. 五个文件清理模块的结果语义一致，并能查看逐项失败原因。
7. 首页和清理页符合 A 方向，保留水墨辨识度且明显降低卡片噪声。
8. 深浅色、键盘、VoiceOver、Reduce Motion 和大字号无阻断性问题。

## 13. 实施顺序

1. 先建立扫描状态、规则模型、所有权去重和测试，不改 UI 行为。
2. 修复 Apple 缓存保护、扫描代次和外置卷恢复等 P0/P1 问题。
3. 增加浏览器、开发/AI 工具和卸载残留规则，逐条以测试限定边界。
4. 引入 `CleanupExecutor` 与统一逐项结果模型，逐个迁移模块。
5. 建立统一页面骨架、筛选、底部操作条和结果 sheet。
6. 按首页、Clean、Purge/Large Files、Docker、Uninstaller、Status 顺序迁移视觉和交互。
7. 完成全量测试、快照、Release、安装与可访问性走查。

每一步保持可构建；安全与规则变化先红测、再最小实现、再重构。视觉迁移不与删除策略变化混在同一个不可验证的大改动中。

## 14. 风险与控制

- **规则扩充误删：** 只加入明确可再生子目录；不对未知 Application Support 做递归猜测；建议项默认关闭。
- **Apple 保护放宽过度：** 只对白名单规则豁免通配保护，不修改关键路径 denylist。
- **共享容器误归属：** Group Containers 仅提示，不自动清理。
- **外置卷恢复信任扩大：** 可信根由实际删除结果与卷信息派生，并继续校验指纹和目标占用。
- **重构造成行为漂移：** 先为现有行为补契约测试，再迁移到执行器；Docker CLI 保持独立。
- **UI 重构影响 M27 未提交成果：** 复用现有 InkTypography、InkElevation、InkWash 和模块色，分页面迁移并保留对照快照。
- **项目体量失控：** P0/P1 先完成；覆盖与视觉按独立可验证批次落地，不顺带加入非目标功能。

## 15. 最终产品体验

完成后，净山仍是一款“先让用户看清楚，再允许清理”的本地 macOS 工具。它不会通过夸张数字或默认全选制造清理焦虑；相反，它会明确告诉用户扫描到了什么、哪里没扫到、为什么某项受保护、哪些只是建议，以及操作后如何恢复。视觉上保留独有的山水气质，但把专业感建立在信息结构、反馈完整性、原生交互和安全可解释性上。
