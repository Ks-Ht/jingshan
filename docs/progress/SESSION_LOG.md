## 2026-07-05 会话 1（续六）：M7 Docker 专项清理模块 + 全面安全审计
- 用户要求新增 Docker 专项清理模块（容器/镜像/构建缓存/其他可清理项，用户自选，危险项要备注清理后果），并在完成后做一次全面安全审计（不删错文件、危险项不默认勾选、备注映射准确性、以及其他方面）。
- 设计决策：Docker Desktop 在 Mac 上把容器/卷跑在 Linux 虚拟机里，`docker volume inspect` 的 `Mountpoint` 是虚拟机内部路径，不是 Mac 真实路径——这意味着 Docker 清理**绝不能**复用 `DeletionEngine`/`PathValidator`（那套是给主机文件系统设计的），必须整体通过 `docker` CLI 子进程操作。据此新增独立的 `JingshanCore/Sources/JingshanCore/Docker/` 模块：`DockerCommandRunning` 协议 + `DockerCLI`（`Process` 封装，数组传参无 shell 注入风险，超时用 `DispatchQueue.global().asyncAfter` + `NSLock` 保护的一次性 resume）、`DockerAvailability`（检测安装+daemon 运行状态）、`DockerResource`（`DockerRiskLevel` safe/caution/destructive 三级 + `DockerCleanableItem`）、`DockerResourceScanner`（解析 `docker ps -a -s`/`docker images -f dangling=true`/`docker system df`/`docker volume ls -f dangling=true` 的 NDJSON 输出）、`DockerCleanupEngine`（唯一删除入口，dry-run 支持）、`DockerOperationLogger`（独立日志文件 `docker-operations.log`）。v1 明确不做"已打标签但未使用的镜像"（跨版本可靠判断太难）和网络清理（对磁盘空间影响可忽略）。
- 风险分级与默认勾选：运行中容器（destructive，`docker rm -f`，默认不选）、已停止容器（caution，默认选，这是日常清理的主力）、悬空镜像（safe，默认选）、构建缓存（safe，聚合成一项，默认选）、悬空数据卷（destructive，默认不选，风险备注强调"可能是数据库或持久化数据，删除后无法恢复"）。
